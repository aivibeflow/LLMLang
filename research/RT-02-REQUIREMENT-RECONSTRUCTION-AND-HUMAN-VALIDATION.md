# RT-02 — Requirement Reconstruction and Human Semantic Validation

**Status:** Research proposal and worked example; not a normative LLMLang decision  
**Updated:** 2026-11-20  
**Research area:** RT-02 Intent, requirements, and specification model  
**Related work:** [Scenario 15 — Business Intent to Formal Contracts](RESEARCH-SCENARIO-15-BUSINESS-INTENT-TO-FORMAL-CONTRACT.md), [Scenario 17 — Typed Requirement IR](RESEARCH-SCENARIO-17-TYPED-REQUIREMENT-IR.md), [Scenario 18 — Requirement Evolution and Semantic Impact](RESEARCH-SCENARIO-18-REQUIREMENT-EVOLUTION-AND-SEMANTIC-IMPACT.md), [NASA FRET](https://software.nasa.gov/software/ARC-18066-1), [FRET source repository](https://github.com/NASA-SW-VnV/fret)

## 1. Research question

After LLMLang transforms a user's natural-language request into a typed and possibly formalized requirement, can it reconstruct a faithful, human-readable account of the semantics represented by that formal model, so that an authorized stakeholder can detect omissions, additions, and incorrect interpretations before the contract is accepted?

The proposed capability is **Requirement Reconstruction**; the human review stage is **Human Semantic Validation**.

The direction is asymmetric:
- Forward processing starts from immutable user intent, elicits clarification, and constructs a typed requirement model and formal candidates.
- Reconstruction starts from the resulting typed/formal model and explains what that model actually says.
- The reconstructed explanation must not be generated by simply paraphrasing the original prompt, because that could hide errors introduced during formalization.

Reconstruction is a review aid, not proof that the formal model captures the user's true intent. Human acceptance remains a separate authority decision.

## 2. Worked end-to-end example

The example is:

> If an order is paid and the item is in stock, the system must confirm the order within 5 seconds.

All clarifications below are hypothetical answers for this worked example. They are not inferred facts or accepted LLMLang requirements.

### 2.1 Human Intent

Preserve the exact utterance as an immutable source:

| Field | Value |
|---|---|
| Source ID | `INTENT-ORDER-001` |
| Kind | User statement |
| Text | “If an order is paid and the item is in stock, the system must confirm the order within 5 seconds.” |
| Status | Not yet clarified |

Do not silently normalize “paid”, “in stock”, “confirm”, or “within 5 seconds”. The source is evidence of what was said, not yet a complete contract.

### 2.2 Requirement elicitation

The elicitation pass identifies unresolved dimensions and asks targeted questions. It proposes alternatives but does not select one on the user's behalf.

| Dimension | Ambiguity | Example alternatives |
|---|---|---|
| Temporal origin | From when are five seconds measured? | Payment provider success; system registration of payment; moment all conditions become true |
| Confirmation meaning | What observable event counts? | Status transition; customer notification; both |
| Inventory semantics | What does “in stock” mean for this order? | Stock observed at payment; successful reservation; stock remains available until confirmation |
| Failure behavior | What if reservation fails? | Keep pending; reject/cancel; manual review; another explicit policy |
| Repeated events | What if payment or inventory events are delivered more than once? | Specify idempotency separately if required |

The output is a clarification request with unresolved items, alternatives, and source references.

### 2.3 Clarification decisions

For this example, assume the user explicitly answers:

1. Start the five-second clock when the order service registers successful payment.
2. “Confirm” means changing the order status to `confirmed`; customer notification is not implied.
3. The inventory condition means the item has been successfully reserved for this order.
4. If reservation fails, the order must not be automatically confirmed.

Each answer becomes an immutable clarification decision recording the question, selected answer, decision-maker/authority, revision metadata, and source reference.

These decisions refine but do not overwrite the original statement. “Item is in stock” and “item is reserved for this order” are not synonyms; reservation is selected here only because the hypothetical user explicitly chose it.

### 2.4 Typed Requirement IR

A simplified illustrative representation:

```json
{
  "requirement_id": "REQ-ORDER-001",
  "kind": "business_requirement",
  "owner": "order_service",
  "source_refs": ["INTENT-ORDER-001"],
  "clarification_refs": [
    "DECISION-ORDER-001",
    "DECISION-ORDER-002",
    "DECISION-ORDER-003",
    "DECISION-ORDER-004"
  ],
  "trigger": {
    "event": "payment_succeeded_registered",
    "clock_origin": "event_registration"
  },
  "condition": {
    "predicate": "inventory_reserved_for_order"
  },
  "required_behavior": {
    "action": "set_order_status",
    "value": "confirmed"
  },
  "temporal_bound": {
    "relation": "no_later_than",
    "duration": 5,
    "unit": "seconds",
    "origin": "payment_succeeded_registered"
  },
  "exception": {
    "condition": "inventory_reservation_failed",
    "behavior": "must_not_auto_confirm"
  },
  "assumptions": [],
  "unresolved": []
}
```

This is a readable sketch, not a final schema or a claim that the current prototype accepts this exact shape. Production IR must use typed events, predicates, actions, temporal bounds, exceptions, and explicit provenance rather than treating these strings as executable semantics.

Every semantic clause must trace to the original source or a clarification decision. Unlinked clauses, unresolved assumptions, and unsupported interpretations remain visible and block unjustified acceptance.

### 2.5 Formalization

The typed requirement can be mapped to a suitable formalism. FRET/FRETISH is a candidate for temporal requirements; other classes may need other analyzers.

| Field | Candidate meaning |
|---|---|
| Scope | Relevant order-service execution interval |
| Trigger/condition | Successful payment registration and successful reservation for the order |
| Component | `order_service` |
| Timing | Confirmation no later than five seconds after payment registration |
| Response | Order status becomes `confirmed` |
| Exception | Failed reservation forbids automatic confirmation |

A simplified temporal sketch is:

[
G((P \land R) \rightarrow F_{\leq 5s} C)
]

where (P) means payment success was registered, (R) means the order's inventory reservation succeeded, and (C) means the order status became confirmed.

This is only a semantic sketch, not exact FRETISH syntax or a complete encoding of the exception. Before claiming full fidelity, the model must define whether reservation is required at the trigger instant or may complete later, how the deadline applies if it completes later, and what event establishes reservation failure.

### 2.6 Semantic validation and scenarios

The analyzer checks the typed/formal model within its declared scope. It can detect malformed structure, unresolved references, contradictions, underdetermination, and some unrealizable combinations. A finite-model result is not proof of requirement completeness or business correctness.

| Scenario | Observed events | Expected assessment |
|---|---|---|
| Successful path | Payment registered at 0s; reservation succeeds at 0.2s; status becomes `confirmed` at 3s | Satisfies deadline |
| Late confirmation | Payment registered at 0s; reservation succeeds at 0.2s; status changes at 7s | Violates deadline |
| Reservation failure | Payment registered; reservation explicitly fails; order is not auto-confirmed | Satisfies stated exception |
| Missing confirmation | Payment registered; reservation succeeds; no confirmation by 5s | Violates deadline |
| Payment failure | Payment is not successfully registered | This requirement alone does not define the complete behavior |
| Unknown reservation outcome | Payment registered; reservation outcome is unknown | Inconclusive/unknown, not a pass |

Absence of an obligation in this requirement is not permission to invent a business rule. Unknown or out-of-scope behavior stays labelled as such.

A separate rule could conflict with the five-second deadline—for example, a rule forbidding confirmation until an eight-second payment review completes. The analyzer should expose the conflict and assumptions rather than silently choose a winner.

### 2.7 Requirement Reconstruction

After formalization, generate the human-readable explanation **from the typed/formal model**, not from the original prompt.

Example reconstruction:

> When the order service has registered a successful payment and the item has been successfully reserved for that order, the order service must change the order status to “Confirmed” no later than five seconds after payment registration.
>
> If inventory reservation fails, the order must not be automatically confirmed.
>
> This rule does not require sending an email, push notification, or other customer notification.

The reconstruction must expose the semantic commitments introduced during clarification:
- the clock starts when the order service registers successful payment;
- stock availability means successful reservation for this particular order;
- confirmation means the `confirmed` status transition;
- failed reservation prohibits automatic confirmation;
- notification delivery is not part of this requirement.

The review package contains:

1. **Reconstructed Requirement** — readable account of the formal model.
2. **Business Rule Table** — conditions, actions, prohibitions, and exceptions.
3. **Temporal Scenarios** — satisfying, violating, and inconclusive traces.
4. **Counterexamples** — concrete traces demonstrating violations or conflicts.
5. **Semantic Differences** — clauses added, narrowed, omitted, or unresolved relative to the source and clarification record.
6. **Unresolved Questions** — decisions still needed, without inferred answers presented as accepted.
7. **Provenance Links** — clause-level links from reconstructed text to IR nodes, formal clauses, source statements, and clarification decisions.

### 2.8 Human Semantic Validation

The stakeholder reviews the reconstruction, examples, differences, and provenance. The decision is explicit:

| Decision | Meaning |
|---|---|
| `ACCEPT` | Reconstructed meaning accurately represents intended business behavior |
| `REVISE` | Interpretation or formal model must change |
| `CLARIFY` | More information or an authorized decision is required |
| `REJECT` | Proposed formalization is not an acceptable representation |

A revision creates a new semantic value/revision and triggers reconstruction and validation again. It must not mutate an accepted historical value in place. Approval identifies the exact requirement/formal-model revision reviewed, reviewer authority, and evidence package.

Human acceptance does not mean the requirement is consistent, realizable, or correctly implemented; these are separate claims with separate evidence.

### 2.9 Accepted contract and component contracts

Only after semantic review and required formal checks does the candidate become an accepted business contract.

| Component | Candidate responsibility |
|---|---|
| `payment_service` | Publish/record successful payment information with a defined registration event |
| `inventory_service` | Return an explicit reservation outcome for the order |
| `order_service` | Own the confirmation decision, status transition, and five-second deadline |
| `notification_service` | No obligation is implied by this requirement |

This decomposition is a design proposal derived from the accepted contract, not a fact inferred from the original sentence. Component boundaries and ownership need their own design review.

### 2.10 Tests, implementation, and verification

Generate tests from the accepted contract and preserve requirement-to-test traceability. One test may cover multiple clauses, and one clause may require multiple tests or formal obligations.

Illustrative test intent:

```python
def test_confirmation_occurs_before_deadline():
    order = create_order()
    reserve_inventory(order)
    payment_time = register_successful_payment(order)

    process_order(order)

    assert order.status == "confirmed"
    assert elapsed_since(payment_time) <= 5


def test_failed_reservation_does_not_auto_confirm():
    order = create_order()
    fail_inventory_reservation(order)

    register_successful_payment(order)
    process_order(order)

    assert order.status != "confirmed"
```

These are sketches, not executable project tests. A real harness needs a controlled clock and explicit event ordering; it should cover races, duplicate events, delayed reservation outcomes, and the exact deadline boundary when those are in scope.

Implementation agents receive the accepted contract, component contracts, and test/verification obligations. Verification reports what was actually checked, against which exact model and implementation revision, and under which assumptions. A passing finite test suite is not proof of all program behavior.

## 3. Three independent correctness questions

| Claim | Question | Appropriate evidence |
|---|---|---|
| Intent correctness | Did we understand what the user meant? | Clarification history, authoritative sources, reconstruction, human acceptance |
| Contract correctness | Is the formal requirement well-formed, sufficiently determined, consistent, and realizable under stated assumptions? | Typed IR validation, FRET or other analyzers, scenarios, counterexamples |
| Implementation correctness | Does this implementation satisfy the accepted contract? | Tests, model checking, proof/refinement evidence, runtime monitoring where appropriate |

No row subsumes the others. A solver cannot establish that the user intended the formalized rule, and a correct paraphrase cannot establish implementation conformance.

## 4. Reconstruction quality and independence

Compare reconstruction strategies rather than assuming an LLM paraphrase is reliable:

- deterministic rendering from typed IR and formal clauses;
- LLM-assisted explanation constrained by a typed semantic payload;
- an independent model/pass that receives the formal model but not the original prompt;
- a hybrid: deterministic structured facts first, LLM readability improvements second, without changing the semantic payload.

For the primary fidelity test, withhold the original request and clarification history from the reconstruction generator. Supply them separately to a comparator that computes and displays semantic differences. This reduces the risk that the generator merely reproduces the original words and conceals omissions in the formal model.

Independence reduces some risks but is not a guarantee: shared model biases, incorrect IR semantics, and incomplete source-to-formula translation can affect both directions.

## 5. Research questions

1. What semantic information must be reconstructible from Requirement IR without the original prompt?
2. Which constructs admit deterministic rendering, and where is an LLM explanation necessary?
3. How can the system detect omitted, added, weakened, strengthened, or scope-shifted clauses?
4. How should temporal operators, quantification, exceptions, probabilities, state transitions, and ownership be explained without semantic loss?
5. How should assumptions, unresolved dimensions, unknown outcomes, and unsupported constructs be exposed?
6. What is the relationship between FRET/FRETISH explanations and LLMLang's typed Requirement IR?
7. How can each sentence and scenario bind to exact IR/formula nodes and source/decision provenance?
8. How should revisions and supersession invalidate reconstructions and approvals?
9. Which human review protocol reliably detects semantic defects, and how does it vary by risk?
10. What evidence supports a reconstruction-fidelity claim, and what remains human judgement?

## 6. Proposed experiments and acceptance criteria

### Experiment A — Clause-level round trip

Build a curated set covering triggers, conjunction/disjunction, deadlines, response obligations, prohibitions, exceptions, scope, and unknowns. Formalize into typed IR and reconstruct without the original prompt.

Measure clause precision/recall, polarity, scope/quantifier, temporal-origin/bound preservation, exception preservation, invented statements, and provenance coverage.

Acceptance: every reconstructed normative clause maps to a formal source; every in-scope formal normative clause is represented or explicitly marked as omitted from the human summary; unknown semantics are never rendered as settled facts.

### Experiment B — Semantic mutation detection

Mutate one formal dimension at a time: change 5s to 7s, remove reservation, change `must not` to `may`, shift the timing origin, or drop the exception.

Acceptance: all seeded mutations in the supported fragment are detected. Cosmetic/provenance-only changes are not reported as semantic changes.

### Experiment C — Human review effectiveness

Compare review of (1) original prompt only, (2) formal notation only, (3) reconstructed explanation only, and (4) reconstruction plus scenarios, counterexamples, and provenance.

Measure defect detection, false acceptance, review time, confidence calibration, and risk-class differences. Include domain stakeholders. Select thresholds before the study and report sample size and uncertainty; anecdotal demonstrations are insufficient.

### Experiment D — Temporal and scenario fidelity

Use FRET or another suitable backend for a bounded temporal subset. Compare formal traces, generated scenarios, and readable explanations before, at, and after deadlines, including missing/delayed events.

Acceptance: satisfying, violating, and inconclusive traces are consistently classified within the declared model and time semantics. Backend limits are explicit.

### Experiment E — Evolution and approval invalidation

Change one accepted clause, then separately change only explanatory wording or provenance. Semantic changes regenerate affected reconstructions and require fresh approval; provenance-only changes do not silently mutate semantic identity or trigger unjustified re-verification.

Use Scenario 18's separation of semantic value, snapshot selection, dependency edges, and lineage.

## 7. Failure policy and trust boundaries

- Reconstruction failure, unsupported constructs, missing provenance, or unresolved semantics produce explicit incomplete/unknown results, never a success-shaped summary.
- A readable explanation is not evidence that the underlying formalization is correct.
- Consistency/realizability results are limited to the encoded model, assumptions, supported fragment, and resource bounds.
- The LLM may propose clarifications and revisions but cannot approve a business rule unless separately authorized.
- Human approval binds to the exact semantic revision and evidence package reviewed.
- Implementation verification remains separate from reconstruction and human acceptance.

## 8. Relationship to existing LLMLang research

- **Scenario 15** establishes the controlled path from human intent through clarification to candidate formal contracts, with human acceptance distinct from LLM proposal.
- **Scenario 17** supplies the typed, provenance-carrying Requirement IR, ambiguity/contradiction/underdetermination analysis, and finite scenario generation.
- **Scenario 18** supplies immutable semantic revisions, snapshot-local selection, semantic dependency impact, and separate lineage/provenance.
- **FRET** is a candidate formalization/explanation backend for suitable temporal requirements. It does not replace LLMLang elicitation, provenance, or human authority.
- **RT-14 Knowledge Context and Task Context** may supply versioned sources and review-task scope/obligations, but neither silently becomes the authority for business meaning.

This research extends RT-02; it does not supersede Scenarios 15, 17, or 18 and does not make FRET mandatory for every requirement.

## 9. Conclusion and non-decisions

Requirement Reconstruction and Human Semantic Validation should be investigated as an explicit stage between formalization/semantic analysis and acceptance of the business contract.

This proposal does not select a canonical reconstruction schema, deterministic versus LLM rendering, a mandatory FRET dependency, universal acceptance thresholds, or mandatory review depth. It does not claim that reconstruction proves intent correctness or that an accepted contract proves implementation correctness.

The next step is to run Section 6's experiments against the existing Scenario 15/17 models and prototype, then update the RT-02 dependency map and candidate architecture only from evidence.
