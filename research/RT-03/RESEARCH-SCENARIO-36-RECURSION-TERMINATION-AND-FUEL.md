# Research Scenario 36 — Recursion, Termination, and Execution Budgets

**Status:** evidence collected; comparison open; no vector selected  
**Updated:** 2026-11-19  
**Aspect:** RT-03 semantics × RT-04 effects/types × RT-07 verification × RT-10 runtime

## Question

How should LLMLang distinguish a recursive computation that returns, one that diverges, and one stopped by a resource limit? What guarantees should the type checker, verifier, and runtime make about termination and resource budgets?

This is an open semantic question: the current executable A/D evaluators and typed-call experiment have no recursive calls. Their finite test coverage does not define the behavior of general recursion or exhaustion.

## Candidate vectors

| Vector | Rule | Benefits | Costs and risks |
|---|---|---|---|
| **T — Total-by-default recursion** | Every recursive definition must pass structural or well-founded termination checking. Nontermination is rejected statically. | Termination claims compose with total-function reasoning; proofs can reduce recursive definitions when the termination evidence is accepted. | Some useful searches, servers, interpreters, and reactive loops are naturally nonterminating; termination analysis is incomplete and may require annotations/proofs. Requires a distinct model for productive co-recursion. |
| **P — General recursion with partiality** | General recursion is allowed; divergence is part of program behavior. Static proofs must distinguish partial code or treat it opaquely. | Directly expresses long-running and potentially nonterminating computations; familiar systems-language model. | Termination cannot be inferred from a return type; equivalence and proof are harder; stack, time, and memory failures may vary with implementation. |
| **D — Typed divergence effect** | A function that may diverge carries an explicit `div`/`Dv` effect, inferred or declared and propagated through calls. The effect classifies termination behavior; it need not be a user-catchable handler operation. | Callers and effect-polymorphic combinators can distinguish total computations from potentially divergent ones without rejecting all general recursion. Koka demonstrates row-polymorphic callback propagation; F* demonstrates isolation of partial computations from a total logical core. | Sound inference relies on call-graph/effect completeness and sound escape hatches; higher-order effect polymorphism is not equally expressive in all systems (F* documents a limitation). A `div` label does not prove nontermination, bound time, or provide a runtime recovery mechanism. |
| **F — Explicit fuel/budget semantics** | Evaluation receives a declared step or cost budget; exhaustion is a distinct outcome. Recursion may be total or partial inside that envelope. | A bounded run has a reproducible stopping criterion if the cost model is specified; useful for verifiers, sandboxed execution, and deterministic replay. | Fuel measures abstract language steps, not wall time or exact machine cost; instrumenting and preserving the count through optimization is a semantic and compiler obligation. Caller/callee ownership and cleanup at exhaustion must be defined. |
| **M — Metered VM gas** | The runtime charges fuel to VM operators/instructions, possibly with configured variable costs; reaching zero traps or yields according to the runtime API. | Supports deterministic per-runtime work budgets without defining source-language cost for every expression. Useful in sandboxes and hosted execution. | Cost is tied to VM version, cost schedule, instrumentation, and host-call policy; equivalent source programs may consume different amounts across compilation/lowering versions. Trap/yield behavior and cleanup are runtime contracts. |
| **E — External runtime limits** | Source semantics permits unbounded computation; implementation or embedder may terminate it on stack, memory, or execution limits. | Fits native/VM deployment and operational limits without imposing one source-level cost model. | Result may depend on implementation, host, and configuration; exact error class and cleanup behavior may not be portable. Evidence must record runtime/limit identity and must not treat timeout as semantic divergence or success. |

These vectors can be combined. A particularly plausible comparison is total-by-default for proof-facing pure functions, explicit partial/effectful boundaries for servers and interpreters, and an external runtime budget for operational safety. That combination remains a hypothesis, not a recommendation.

## Prior-art observations

Lean requires recursive definitions either to be justified to its kernel by a termination strategy or made opaque using `partial`; the reference describes several structural and well-founded strategies. Lean's `partial` declarations are completely opaque to the logic, while `partial_fixpoint` supports a more explicit partial-function account. This makes the proof boundary visible rather than pretending that an unproved recursive function is total. [Lean Reference: recursive definitions](https://lean-lang.org/doc/reference/latest/Definitions/Recursive-Definitions/) · [Lean Reference: definitions](https://lean-lang.org/doc/reference/latest/Definitions/Definitions/).

Koka tracks possible nontermination as a `div` effect, separate from `exn`, nondeterminism, state, and console effects; it also infers and propagates effects polymorphically. Its documentation calls the no-effect case `total` and the combination `<div, exn>` `pure`, which shows that purity and termination are distinct properties. F* has a primitive `Dv` effect: `Tot` has total-correctness semantics, while `Dv` permits divergence and retains partial-correctness guarantees (“if it terminates, the result satisfies the type”). F* says `Dv` disables termination checking and is outside its logical core, so extrinsic proofs cannot assume evaluation yields a value. These systems show that tracking divergence in a type/effect boundary is distinct from proving termination or adding fuel. [Koka effect types](https://koka-lang.github.io/koka/doc/book.html#effect-types) · [F* divergence effect](https://fstar-lang.org/tutorial/book/part4/part4_div.html).

### How divergence flows through higher-order calls

The two systems differ in how reusable higher-order APIs express that flow:

| System | Recursive and totality rule | Higher-order propagation | Limitation or escape hatch |
|---|---|---|---|
| Koka | Inferred effect rows include `div` when a function may diverge; an effect-free `total` type is documented as mathematically total. The current standard-library docs characterize termination analysis as very limited: it recognizes direct recursion on inductive datatypes. | `map` is polymorphic in callback effect `e`: a callback `a -> e b` makes `map` return `e list<b>`. `while` explicitly adds `div` to the shared predicate/action effect row because iteration may not terminate, and call-site inference unions the effects of both callbacks. | The limited termination analysis means a complex recursive cycle that is not recognized as direct structural recursion needs to remain possibly-diverging unless justified through a documented unsafe escape. `pretend-decreasing` and `pretend-no-div` are explicitly unsafe and can make actual divergence invisible in the effect type. |
| F* | A recursive `Tot` function needs a well-founded decreasing measure; the same check applies to every edge in a mutually recursive group, whose members are checked under measure-restricted recursive types. `Dv` skips termination checking and means partial correctness: if it returns, the result satisfies its type. The effect order `Tot < Dv` permits weakening total work to `Dv`, but prohibits `Dv` work from flowing into `Tot`, protecting the logical core. | Function values carry a computation type for their body, so a callback that may diverge must be represented with `Dv`; a caller cannot claim `Tot` if its body depends on that callback. | F*'s official higher-order `map` tutorial says arbitrary effect-polymorphic `map : (a -> E b) -> E ...` is unsupported there; one can annotate a particular effect (e.g. `ML`) or provide effect-specific variants. Thus `Dv` isolation is strong, but callback effect abstraction is less general than Koka's row-polymorphic API. |

For Koka, the primary documentation gives concrete signatures and propagation examples for [effect-polymorphic `map` and `while`](https://koka-lang.github.io/koka/doc/book.html#polymorphic-effects), and its [unsafe divergence primitives](https://koka-lang.github.io/koka/doc/std_core_undiv.html) state that compiler termination analysis only recognizes direct recursion on inductive datatypes. For F*, the [termination guide](https://fstar-lang.org/tutorial/book/part1/part1_termination.html) spells out measure checks across mutual-recursive calls; the [`Tot`/`Dv` order and partial-correctness contract](https://fstar-lang.org/tutorial/book/part4/part4_div.html), [computation effects on function arrows](https://fstar-lang.org/tutorial/book/part4/part4_computation_types_and_tot.html), and [higher-order map/effect-polymorphism limitation](https://fstar-lang.org/tutorial/old/tutorial.html#higher-order-functions-on-lists) support the rest of the comparison. The `map` example is in F*'s older official tutorial; the [ICFP 2015 F* design paper](https://fstar-lang.org/papers/icfp2015/full.pdf) also describes lack of parametric polymorphism over effects as a deliberate inference tradeoff. Recheck this limitation against any specific F* release selected for future experiments.

Koka's type library gives a further heap-boundary example. The `div` effect is a built-in effect handled by the system, rather than a user-defined operation that an ordinary effect handler consumes. Its `hdiv` constraint is generated when reading from a heap: if the read type contains a reference to that same heap, the surrounding effect row must include `div`. The documentation says this catches divergence from self-referential functions stored in the heap. Thus callback propagation through explicit arguments is not the full higher-order audit: a language with mutable heap and stored closures also needs to account for possible divergence revealed by heap reads. [Koka primitive effect and `hdiv` documentation](https://koka-lang.github.io/koka/doc/std_core_types.html#hdiv).

This comparison suggests five separate LLMLang checks: (1) does divergence propagate through every direct and higher-order call path; (2) can generic combinators preserve an unknown callback effect without losing `div`; (3) can mutable heap reads reveal closures or recursive references whose calls may diverge; (4) how is every recursive strongly connected component classified, including cross-member descent proofs; and (5) which trusted or unsafe annotations may suppress the inferred divergence effect? F* shows that a mutually recursive group can be accepted as `Tot` when the checker establishes a well-founded decrease across each recursive call, including lexicographic phase changes between members. Koka documents a narrower built-in analysis, so a conservative language would need to classify unproven recursive cycles as possibly-diverging or require an explicit proof boundary. A possibly-diverging effect is a conservative possibility label, not a proof that the specific call actually diverges, a bound on execution, or a catchable runtime event. A total annotation is meaningful only if unknown calls, virtual dispatch, callbacks, heap-stored functions, and recursive strongly connected components cannot bypass the termination/effect check.

Rust permits general recursion but does not make stack exhaustion an ordinary `Result` value. The Rust RFC error conventions classify stack overflow and out-of-memory as catastrophic errors; it states that stack overflow currently aborts the process. Rust panic strategy is separately configurable: `unwind` walks the stack and may be recoverable, while `abort` does not unwind and permits different optimization assumptions. These behaviors demonstrate that recoverable panic, catastrophic runtime failure, and domain `Result` are separate outcome classes. [Rust RFC 236: error conventions](https://rust-lang.github.io/rfcs/0236-error-conventions.html) · [Rust Reference: panic](https://doc.rust-lang.org/reference/panic.html).

WebAssembly defines traps for certain instruction conditions, while its implementation-limits appendix permits an implementation to terminate computation when runtime limits are exceeded and report an embedder-specific error. The spec states concrete limits may depend on implementation or embedder circumstances. A runtime budget can therefore be an execution boundary without being a portable source-level step count. [WebAssembly Core Specification 3.0: implementation limitations](https://webassembly.github.io/spec/core/appendix/implementation.html).

Wasmtime supplies a concrete **VM-metering** example beyond the WebAssembly source semantics. With `consume_fuel`, compiled Wasm code maintains a precise instruction count and traps when fuel is exhausted; the cost of each Wasm operator can be configured, including variable costs. Its separate epoch-interruption mechanism checks periodically and is intended for cooperative time slicing; a configured fuel async-yield interval can yield execution to the host executor. Fuel interruption has more execution overhead than epochs. Therefore an exact instruction meter and a responsiveness/deadline mechanism are separate runtime choices, and neither is automatically an LLMLang source-level cost model. [Wasmtime interrupting execution](https://docs.wasmtime.dev/examples-interrupting-wasm.html) · [Wasmtime `Config`](https://docs.rs/wasmtime/latest/wasmtime/struct.Config.html).

## Observable outcome model to compare

For one computation, record `(value, terminal outcome, trace, final store/resources, budget/runtime identity)`:

| Case | Candidate terminal observation |
|---|---|
| Recursive function returns | `Returned(value)` |
| Domain failure is returned | `ResultError(error)` |
| Declared budget is exhausted | `FuelExhausted(remaining=0)` or another explicitly chosen budget outcome |
| Runtime limit stops execution | `RuntimeLimit(kind, implementation/configuration)` or host-level failure |
| No finite result exists absent a stop limit | `Diverges` as a semantic classification; an actual executor may only observe that it has not returned yet |
| Unrecoverable runtime fault | `Aborted(fault-class)` with explicit cleanup/trace guarantees |

The table is a candidate vocabulary. In particular, a timeout observed by a test harness cannot prove divergence, and a runtime interruption cannot be silently converted into a domain error.

## Budget layer and effect/cleanup boundary

Budget placement and exhaustion handling are separate dimensions:

| Layer/policy | What is counted or stopped | Semantics of completed effects | Cleanup expectation |
|---|---|---|---|
| Source fuel | Abstract source transitions under a language-defined cost relation | Prior observable effects remain unless an explicit transaction effect says otherwise; fuel affects the program outcome | The language can define exhaustion as a structured terminal outcome and run cleanup, but must specify whether cleanup gets reserved fuel and how cleanup errors combine with `FuelExhausted` |
| VM operator gas | Runtime instructions/operators under a versioned cost table, as in Wasmtime fuel | A trap stops guest computation; the VM store is not a general external transaction and host-import effects need an embedder contract | Do not assume guest finalizers run on trap; the host must dispose of runtime resources according to the embedding API |
| Verifier/harness cap | Wall time, memory, steps, or external job quota around evaluation/proof | This is evidence collection stopping, not a source program result; return `UNKNOWN`/incomplete evidence unless the harness proves a specific semantic outcome | Harness cleanup/recovery is tool policy, not LLMLang source cleanup |
| Cooperative cancellation | A scheduler/host requests that a task stop at a specified cancellation point | Previously completed effects remain visible unless a declared transactional boundary compensates them | Structured cleanup can run on cancellation if polling points and cleanup guarantees are defined |
| Abort/trap without unwinding | Process or guest stops without ordinary control return | Earlier external effects may already have escaped; a runtime trap does not itself promise rollback of the whole invocation | No source-level cleanup should be assumed; Rust's `abort` panic strategy explicitly skips destructors, unlike unwinding panics |

The WebAssembly core says an instruction trap aborts the computation and makes no further store modifications; it does not state that earlier state changes or embedder side effects are rolled back. Rust's `unwind` handler runs `Drop` for live frame values while unwinding, whereas `abort` is non-recoverable and does not run destructors. Together these sources show that (1) completion/stop classification, (2) rollback, and (3) resource finalization must be specified independently. [WebAssembly Core Specification](https://www.w3.org/TR/wasm-core/) · [Rust Reference: panic and unwinding](https://doc.rust-lang.org/reference/panic.html).

## Compatibility conditions and risks

- RT-03 evaluation, RT-04 effects and result types, RT-07 proof claims, and RT-10 runtime limits must agree on the terminal outcome vocabulary.
- A divergence effect is a static possibility summary, not a dynamic error result: handlers must not imply they can catch an infinite computation unless cancellation/termination is separately specified.
- Effect inference must propagate divergence through higher-order calls and recursive strongly connected components; incomplete call graphs must remain unknown rather than infer `total`.
- Unknown callback effects need an explicit effect parameter/row or a conservative upper bound. Any unsafe escape that suppresses divergence (as Koka's documented `pretend-no-div` does) must be visible in trust/evidence policy; ordinary handlers must not catch `div` as if it were a resumable error.
- A proof over a potentially diverging function must state whether it is total correctness, partial correctness conditional on return, or an intrinsic property of a computation representation.
- If fuel becomes a source-visible input, it affects function behavior, semantic identity, cache keys, and verification inputs. If it is only a verifier parameter, the verifier must not claim an unbounded source theorem from a bounded run.
- VM-meter fuel is a runtime/profile input: bind the engine/version, operator cost schedule, host-import budget rules, and interruption mode into runtime/evidence identity instead of silently treating it as source semantics.
- If compiler optimizations change the number of abstract steps, either the fuel semantics must be preserved by the lowering or the language must identify the execution layer whose steps are counted.
- Budget exhaustion during effects, cleanup, or after ownership transfer must specify whether earlier effects persist, whether cleanup can run, whether fuel is reserved for cleanup, and how the resource-state/error-with-value invariants from COR-13 are preserved.
- Co-recursion, lazy structures, asynchronous waits, and actor liveness require separate productivity/fairness questions; structural termination of a pure call does not establish scheduler progress.
- Wall-clock deadlines and memory caps are environment/runtime inputs, not substitutes for a portable cost semantics.

## Falsification and discriminating experiment

A total-by-default vector is weakened if representative RT-01 workloads require unbounded service loops and cannot isolate them behind an explicit partial/effectful boundary without unacceptable complexity. A general-recursion vector is weakened if the required proof and cache-reuse claims depend on termination that cannot be established modularly. A typed-divergence vector is weakened if higher-order or mutually recursive effect inference marks a potentially diverging path as total, a generic callback API cannot preserve its effect, an unsafe divergence escape is hidden from evidence inputs, or `div` is mistaken for a catchable exception. A source-level fuel vector is weakened if two conforming evaluators or a semantics-preserving optimization disagree on fuel exhaustion. An external-limit-only vector is weakened if identical verification inputs can produce incompatible terminal observations across supported runtimes.

The first observation probe is [`rt03_fuel_cleanup.py`](../PROTOTYPES/RT-04-01/rt03_fuel_cleanup.py). With a budget of two ordinary transitions, it records an external write and acquires a resource, then exhausts before the next body transition. Reserved cleanup allowance yields `FuelExhausted`, preserves the write trace, and releases the resource. Without reserved allowance, cleanup itself cannot run (`CleanupFuelExhausted`) and the resource remains active. An abortive trap also preserves the earlier modeled write and leaves the resource active, with no guest cleanup trace. The probe deliberately treats these as separate terminal/resource outcomes; it has no real host side effects, failure-prone cleanup, ownership transfer, or language/runtime implementation.

This establishes a useful discriminator, not a selected rule: if structured cleanup is promised on source-fuel exhaustion, the language must say whether cleanup uses reserved fuel or can itself fail for lack of fuel, how cleanup failures combine with the primary exhaustion, and whether nontermination inside cleanup is possible. A runtime trap may not provide that source-level guarantee. The fuel × owned-return probe below addresses the first ownership interaction; the COR-07 comparison below refines cleanup-error precedence. Remaining work includes the reserve-size/divergence cases described there, then a recursive source fragment with terminating structural/non-structural cases, divergence, exhaustion at multiple boundaries, a reference interpreter versus small-step evaluator, and an optimized lowering. Source syntax, runtime correspondence, and independent review remain necessary before treating the result as evidence about LLMLang source programs.

### Cross-check with COR-13 owned returns

[Scenario 35 / COR-13](../RT-04/RESEARCH-SCENARIO-35-RESOURCE-RETURN-AND-CLEANUP.md) already separates staged return (`reserve_then_commit`) from transfer-before-cleanup (`transfer_then_cleanup`). Combining its ownership boundary with the fuel probe adds a second axis: whether cleanup can execute after the ordinary budget is exhausted. This is a derived design matrix, not yet an executable cross-product:

| Return timing × exhaustion rule | Handle owner when local cleanup is reached | Required observable distinction |
|---|---|---|
| Transfer first; cleanup reserve available | Caller owns `handle` | Cleanup can finish, but the call still needs an explicit policy for whether the primary outcome remains `FuelExhausted` and whether that outcome may carry the handle. A plain error without value loses the caller's ownership obligation. |
| Transfer first; no cleanup reserve | Caller owns `handle`; local resource remains active | Must preserve both prior effects and caller ownership while reporting cleanup blocked by fuel. A `Result<Owned<T>, E>` cannot represent value plus error; COR-13 calls for an error-with-value style outcome. |
| Stage result; cleanup reserve available | Callee owns pending `handle` until commit | If fuel exhaustion initiated unwinding, the language must say whether successful local cleanup permits committing a value despite exhaustion, or whether the pending handle is disposed and the terminal outcome remains exhaustion. These are observably different. |
| Stage result; no cleanup reserve | Callee owns pending `handle`; local resource remains active | Returning only `FuelExhausted` can hide two live cleanup obligations. The outcome must preserve the pending value/debt, define bounded follow-up cleanup, or classify the event as an abortive runtime failure with explicit leak/host-disposal semantics. |

The cross-probe [`rt03_fuel_owned_return.py`](../PROTOTYPES/RT-04-01/rt03_fuel_owned_return.py) instantiates this boundary under one explicit candidate rule: fuel exhaustion prevents normal commit; transfer-first leaves the handle with the caller; staged return disposes the pending value; reserved cleanup runs and can fail independently. In the five displayed cases, staged return plus successful reserved cleanup disposes both values but still reports fuel exhaustion; failed cleanup retains both cleanup debts. With depleted fuel, both staged obligations are marked blocked/debts. Transfer-first preserves caller ownership in both cleanup modes; the observation needs to carry `handle` alongside fuel exhaustion, while the temporary remains a cleanup debt if cleanup fails or is blocked. The result records primary exhaustion, returned value, effect trace, attempted/blocked cleanup, and owner map as separate fields, so no owner is silently dropped in these examples.

[`rt03_fuel_owned_return_audit.py`](../PROTOTYPES/RT-04-01/rt03_fuel_owned_return_audit.py) independently derives the expected owner map and cleanup obligations from each observation's return-timing and cleanup-budget labels. Its eight bounded cases cover both return timings, both cleanup-budget policies, both staged cleanup failure flags when reserved cleanup is available, and local cleanup success/failure after transfer. All eight satisfy the obligation projection: no duplicate owner entry, unaccounted blocked cleanup, or lost completed effect was observed. This is a bounded cross-check of the prototype's outputs, not an independent language semantics or proof that the scenario matrix covers all control flow.

### Cleanup computation and error precedence

COR-07's independent [`rt03_resource_rules.py`](../PROTOTYPES/RT-04-01/rt03_resource_rules.py) specifies bounded cleanup composition. For a body `Result` error with two failing nested releases, it unwinds inner then outer and nests each later `CleanupFailed` around the prior error (`outer` becomes the outermost cleanup error). For cancellation, it preserves the cancellation outcome and appends cleanup failures in LIFO order instead of converting them to a `Result` error. Failed releases leave those resources in `final_resources`. A direct two-frame probe produced these outcomes; the rule model treats each release as one terminating atomic step.

Fuel exhaustion raises two questions that COR-07 does not cover:

| Case | Existing bounded resource rule | Fuel interaction still needed |
|---|---|---|
| Body returns a domain `Result` error; cleanup also fails | Nested `CleanupFailed` wrappers preserve the domain error as `primary` | If exhaustion first initiated unwind, keep `FuelExhausted` as a runtime terminal cause rather than silently reclassifying it as a catchable domain `Result`; define how cleanup errors attach to it |
| Body is cancelled; cleanup fails | Cancellation remains distinct, with cleanup errors accumulated in LIFO order | Define precedence if fuel also runs out during cancellation cleanup: preserve cancellation, fuel exhaustion, or both as structured terminal causes |
| Several resources need cleanup; reserved cleanup fuel is insufficient | Not modeled; all acquired frames are attempted as finite atomic releases | Specify whether remaining frames are skipped and recorded as cleanup debt, get per-resource reserve at acquisition, or cross an abortive fallback boundary |
| Cleanup itself may diverge or issue effects | Not modeled; release always terminates with success or error | No finite reserve guarantees completion for arbitrary cleanup code. Restrict cleanup to terminating/bounded effects, permit interruption with explicit debt, or accept that cleanup can defeat the original fuel stop |

The observed LIFO order and error nesting provide a candidate aggregation rule only for cleanup actions that terminate. They do not settle the representation of a combined primary cause such as `(FuelExhausted, CleanupFailed*)`. A flat ordered list preserves all causes without deep nesting; nested errors preserve the existing COR-07 construction but may obscure the primary stop reason. Cancellation's separate aggregate is another prior-art design point. Compare these forms before defining whether a handler can catch any component.

The finite [`rt03_cleanup_fuel_stack.py`](../PROTOTYPES/RT-04-01/rt03_cleanup_fuel_stack.py) probe compares a shared reserve with the same fixed reserve available separately to each scope. For two scopes (`inner` cost 3, `outer` cost 1), shared reserve 3 runs inner cleanup and leaves outer blocked; shared reserve 4 runs both. Per-scope reserve 3 provides 6 total, runs both, and spends 4. A per-scope reserve of 1 cannot run inner and strict LIFO prevents skipping it to release outer. If inner cleanup fails after consuming its cost, the model records `inner` as retained and continues with outer cleanup while reserve remains. The earlier effect stays visible in every case.

This exhibits the policy trade-off: a shared pool is cheaper but can leave outer obligations partially discharged when the total bound is too small; per-scope reservation can guarantee each declared bound but may reserve more than execution uses and requires knowing a bound at acquisition. Neither guarantees termination if cleanup exceeds its bound or diverges; interruption must expose remaining debts, and cleanup effects/errors need a stable order. The model assumes fixed, positive, terminating costs, one release outcome per frame, and no nested acquisition during cleanup.

The cross-probe's candidate convention—that staged values are disposed on fuel-abort and that depleted cleanup fuel leaves cleanup debt—still needs comparison with alternatives. Next combine the stack reserve probe with body outcomes (`Result` error, cancellation, fuel exhaustion), owned-return timing, cleanup cost/failure, and possible cleanup divergence. Track exact effects, terminal cause ordering, and owners; then connect the boundary to a recursive source fragment and runtime correspondence. No rule is selected here.

### First bounded fuel model

[`rt03_recursion_fuel.py`](../PROTOTYPES/RT-04-01/rt03_recursion_fuel.py) models one recursive function, `countdown(n) = 0 if n == 0 else countdown(n-1) + 1`, and one self-recursive loop. Its explicit abstract source-cost rule charges one unit for function entry, condition test, decrement, and each return addition. This gives `4*n + 2` units for `countdown(n)`; for example, input 3 returns 3 with fuel 14, while fuel 13 stops before the third return addition. Input 0 needs two units (entry and condition).

The loop model reports `FuelExhausted` for every finite budget and separately carries `may_diverge=true`. Thus exhaustion alone cannot distinguish divergence from a terminating computation that needs more fuel; that distinction requires a proof/analysis or an unbounded semantic observation. This experiment defines an abstract source-step accounting rule, not machine instruction gas. No optimized backend was run. If source-visible fuel is chosen, a compiler must preserve the specified abstract fuel observations or expose an explicit cost-preservation relation; counting backend instructions instead makes the budget depend on lowering. The recursion prototype does not model effects, cleanup, stack limits, mutual recursion, or a termination checker; the separate cleanup probe covers only one fixed transition boundary and three cleanup policies.
