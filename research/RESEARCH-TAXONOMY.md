# LLMLang Research Taxonomy

**Status:** Working research-management document; not a language specification or an architecture decision  
**Updated:** 2026-11-20

Scenario 94 compares scheduler fairness and liveness: preemption, weak/strong/bounded runnable-task progress, priority starvation, resource fairness, and structured joining are distinct. The cited guarantees are runtime/profile-specific or conditional; no LLMLang policy is selected and no runtime experiment has been run.

Scenario 95 compares compiler diagnostic models and repair channels for humans and agents. Structured records, text renderers, editor transport, suggested edits, and repair authority are separate; studies of novice humans and LLM-generated explanations do not establish autonomous agent repair quality. No LLMLang diagnostic policy is selected.

Scenario 96 isolates LLVM lowering semantics: immediate/deferred UB and poison are distinct from LLMLang source errors, traps, wrapping results, and memory contracts. A version-pinned source-to-IR corpus remains to be run; no backend or source policy is selected.

Scenario 112 checks explicit starvation cycles: weak fairness excludes a task that stays continuously enabled but allows starvation when it is enabled only intermittently; strong fairness excludes both. A two-task round-robin turn bound assumes both tasks remain runnable and every selection returns. These are abstract finite witnesses, not a runtime result or general liveness proof.

Scenario 113 adds bounded memory-model witnesses and official prior-art comparison to Scenario 61: sequential consistency excludes the both-zero store-buffering result, an abstract independently ordered profile admits it, a stipulated synchronizes-with edge constrains message passing, atomic RMW prevents a lost counter update, and same-location read-read coherence excludes backward observations. Rust/C++20 provide a family of memory orders; Go makes all atomics sequentially consistent and states DRF-SC for race-free programs. Official sources also differ on mixed atomic/non-atomic race boundaries and consequences. The toy relations clarify discriminating outcomes; they are not a complete language, compiler, or hardware memory model.

Scenario 114 isolates release-sequence relay and a C++ version change: before C++20, a same-thread relaxed plain store could extend the release sequence; since C++20 only following RMWs can. An acquire reading an RMW member synchronizes with its release head; reading an equal value written by a same-thread relaxed plain store has that effect only before C++20. An axiom-driven fixture checks the resulting atomic payload outcomes. It does not infer modification order or read-from from code, nor model the complete C++/Rust memory model; no LLMLang rule is selected.

Scenario 115 records C++ fence synchronization conditions and the scope of the `seq_cst` order. Release/acquire fences need a specified read-from link through atomic operations; `seq_cst` operations and fences participate in a constrained total order, but the current draft does not make that order consistent with all happens-before edges when weaker orders are mixed. One axiom-driven fixture checks the payload outcomes from a stipulated fence link. This is not a full fence or mixed-order model; no LLMLang policy is selected.

Scenario 116 compares source memory-order obligations with LLVM IR and target lowering. It proposes source `Relaxed`→LLVM `monotonic` for validation because LLVM `unordered` is weaker and lacks per-object modification-order/coherence guarantees. LLVM atomics in IR are required lock-free, while unsupported widths may fail code generation. Three width-availability policies are compared: target-gated types, a lock-backed fallback, and native atomics plus an explicit fallback API. Source semantics must not inherit incidental IR behavior; fallback changes progress and async/signal properties. No source-to-IR proof or LLMLang atomic availability policy has been validated.

Scenario 117 adds finite fixtures for the three per-object coherence conditions not executed in Scenario 113: write-write ordering, strict read-write source-before-target ordering, and write-read source-at-or-after ordering. It takes happens-before and modification-order premises as inputs and filters read-from candidates; it does not derive these relations or model a complete execution. All four named per-object conditions now have a focused axiom-level fixture, while cross-location, source-derived, compiler, and hardware validation remain open.

Scenario 118 derives modification order, read-from, and happens-before witnesses for fixed atomic load and store sequences. An independent interleaving oracle agrees on global-order witnesses in all 4,096 generated programs. Relaxed and direct release/acquire operations permit additional observed values in 98 of those programs. The experiment supplies a comparison for RT-04, RT-10, and RT-13. [Atomic execution relations](RESEARCH-SCENARIO-118-ATOMIC-EXECUTION-RELATIONS.md)

Scenario 119 infers obligations in a matched call result from lexical scopes and close contracts. In 4,096 concrete inputs, the result shapes agree with the disposition model. Covering every tag can still miss a new obligation when a close contract changes. This connects RT-03 transfer semantics to RT-04 resource checks and RT-05 interface compatibility. [Ownership in matched call results](RESEARCH-SCENARIO-119-OWNED-RESULT-MATCHING.md)

Scenario 120 measures cleanup return codes and destruction timing for a SQLite connection with prepared statements. The probe distinguishes API error reporting from capability availability and remaining cleanup work. This adds implementation evidence for the RT-04 to RT-10 dependency. [Cleanup dependencies in SQLite](RESEARCH-SCENARIO-120-SQLITE-CLEANUP-DEPENDENCIES.md)

Scenario 121 compares static close preconditions, explicit busy recovery, and deferred release with 510 bounded plans. SQLite agrees on the call observations for all 356 admitted plans. A statement owned outside the caller makes local release incomplete, even after the caller finalizes all of its own statements. [Local close recovery](RESEARCH-SCENARIO-121-SQLITE-LOCAL-CLOSE-RECOVERY.md)

Scenario 122 derives dependency coverage from source and call summaries in a bounded close fragment. Its 4,116 executions distinguish incomplete local knowledge from stale runtime knowledge. The native SQLite probe confirms that an empty observation can become stale after a single prepare. [Completeness and freshness of close evidence](RESEARCH-SCENARIO-122-CLOSE-EVIDENCE-FRESHNESS.md)

Scenario 123 compares source admission, a checked snapshot, busy recovery, and deferred destruction on shared inputs. The call boundary distinguishes a retained capability from pending destruction even when the local cleanup diagnostic is identical. [Shared close workload](RESEARCH-SCENARIO-123-CLOSE-CALL-BOUNDARY.md)

Scenario 124 checks close observations across two threads. A separate validation can precede a mutation even when its version check succeeds. A guard must cover the underlying resource across aliases to protect the observation through use. [Close synchronization](RESEARCH-SCENARIO-124-CLOSE-SYNCHRONIZATION.md)

Scenario 125 adds reentry and dependent-kind coverage. An application-defined callback can retain a statement under the same recursive lock, and an active backup stays invisible to the enumerated statement set. [Reentry and coverage](RESEARCH-SCENARIO-125-CLOSE-REENTRY-AND-COVERAGE.md)

Scenario 126 compares canonical role checks with checks by binding name. It explores compatible reservations and acquisition deadlock with two contenders, and checks backup role overlap and initialization failure against SQLite. [Multi-resource FFI roles](RESEARCH-SCENARIO-126-MULTI-RESOURCE-FFI-ROLES.md)

Scenario 127 measures how much static admission depends on alias correlation within and across calls. Its bounded source grammar tracks role identities, conditional release, and what stays live on a refused second call. [Source role correlation](RESEARCH-SCENARIO-127-SOURCE-ROLE-CORRELATION.md)

Scenario 128 compares retention after a known or indeterminate foreign failure. It distinguishes a diagnostic, a usable handle, and a reconciliation obligation over a resource footprint. [Foreign reservation outcomes](RESEARCH-SCENARIO-128-FOREIGN-RESERVATION-OUTCOMES.md)

Scenario 129 distinguishes cancellation acknowledgment from terminal disposition and ties consumption to an invocation. It checks delayed evidence on reused resource roles and repeated delivery after release. [Invocation-specific cancellation evidence](RESEARCH-SCENARIO-129-CANCELLATION-AND-INVOCATION-EVIDENCE.md)

Scenario 130 checks durable invocation generations and result recovery across abrupt process exits. It distinguishes a committed result with a lost response from an unresolved outcome under separate effect and journal commits. [Durable invocation results](RESEARCH-SCENARIO-130-DURABLE-INVOCATION-RESULTS.md)

Scenario 131 composes ordered cleanup, typed return obligations, and alias-sensitive admission. The shared source fixture compares two executions across transfer before and after cleanup. [Shared owned-result workload](RESEARCH-SCENARIO-131-SHARED-OWNED-RESULT-WORKLOAD.md)

Scenario 97 isolates cleanup-error composition from cleanup trigger and resource state. Java try-with-resources preserves a primary exception and suppresses ordered close failures; Go specifies LIFO defer but leaves result composition to code (with `errors.Join` available); Rust `Drop` has no ordinary error result and a second panic during unwinding can abort; Swift `defer` constrains control transfer. A cross-outcome ownership/fuel corpus is proposed, not run; no outcome policy is selected.

Scenario 109 tests optional representation at a minimal JSON boundary: a single optional collapses omitted and explicit-null fields under the chosen mapping, while nested optional and tagged presence preserve absent/null/value. Decode errors and uninitialized reads are separate outcomes. The fixture does not resolve schema, serialization, or ABI policy.

Scenario 110 exhausts a small old/new JSON producer-consumer policy product for one added defaulted field. Old payloads decode with the new default; strict old consumers reject new keys while permissive consumers ignore them and lose the field; changing the default changes interpretation of old payloads. Null and unknown-field policies are separate. No schema standard or LLMLang rule is selected.

Scenario 111 compares unknown serialized sum cases under reject, generic fallback, and opaque-preserve policies. Reject avoids acting on an unrecognized case; fallback accepts but loses the tag/payload; opaque preservation allows semantic relay but not application interpretation, and does not preserve the original bytes. Source exhaustiveness and trust-boundary behavior remain untested. Official prior art differs by format: Protobuf proto3 retains unknown numeric enum values, while closed repeated enums can move them in order; Avro applies a reader enum default or errors; CBOR RFC 8949 supports unknown-tag/simple-value signaling and forwarding. The JSON fixture does not reproduce those implementations.

Scenario 102 compares exact finite, tri-state solver, bounded hybrid, and proof-carrying path-pruning policies. A replayed SAT witness establishes one route; solver timeout/UNKNOWN/error and unverified UNSAT do not prune a may-path. SMT-LIB and Z3 expose tri-state and resource-limit behavior, while the pinned SymPy DPLL API has no documented per-query timeout. A deterministic 128-formula CI cross-check and injected result-policy cases pass; broad timeout behavior, hard formulas, proof checking, and source correspondence remain open.

Scenario 103 uses a one-request POSIX worker to impose a real wall-clock deadline on pinned SymPy DPLL2 despite the API lacking a query timeout. A 12-pigeon/11-hole query is killed/reaped and retained as UNKNOWN; a completed UNSAT response remains untrusted and does not prune. This is a narrow resource-bound experiment, not a worker-pool design or solver trust result.

Scenario 104 exhausts a two-state Boolean local read twice with a toggle write between branches. Reusing the source name as one immutable symbolic value loses both reachable routes; independent versions overapproximate; versions linked by the write transition match the concrete route set. Aliases, calls, loops, and source extraction remain open.

Scenario 105 exhausts call transitions for a Boolean value across caller branches: complete pure, complete toggle, and incomplete/may-write summaries. Unknown or may-alias effects require conservative havoc in the bounded model; treating them as pure drops feasible paths. Source-derived summaries, alias analysis, and call-graph completeness remain open.

Scenario 106 exhausts call-site targets for a callee that toggles the referenced Boolean field. Exact points-to evidence distinguishes a write to the predicate field from a disjoint field; may-alias and incomplete target sets union the possible transitions and retain all routes. Scenario 107 extracts a toggle summary and target set from a bounded Python-shaped AST subset: it covers all concrete routes, but a non-relational branch join loses alias/value correlation and adds infeasible routes. This is not a LLMLang parser or general points-to implementation; source/CFG completeness, scalable path-sensitive analysis, and larger memory regions remain open. Scenario 108's finite path-sensitive enumerator recovers two feasible routes where the joined alias set admits four, while retaining all four routes for an independent target choice; no scalable method or path-completeness claim follows.

## 1. Purpose

This taxonomy defines the research space that must be explored before selecting an integrated LLMLang specification. It is deliberately broader than the current prototype or the next implementation milestone.

A research topic is an area of uncertainty, not necessarily one decision. Each topic may produce several viable development vectors. A vector is a coherent approach or family of choices, with explicit assumptions, evidence, constraints, trade-offs, and relationships to vectors in other topics.

The taxonomy is a living index. It must be revised when research reveals new aspects, splits an area into independent questions, or shows that two apparently separate topics are inseparable.

## 3. Required research artifact

Every research report should identify:

1. Scope, motivating questions, and explicit non-goals.
2. Relevant existing LLMLang assumptions and source documents.
3. Viable development vectors; do not force alternatives where evidence supports only one.
4. For each vector: semantics, assumptions, evidence, benefits, costs, risks, limitations, and open questions.
5. Compatibility conditions and cross-aspect dependencies, linked to stable IDs in [the dependency map](RESEARCH-DEPENDENCY-MAP.md).
6. What would falsify or materially weaken the vector.
7. Follow-up experiments or research needed to raise confidence.
8. A concise machine-readable or tabular option summary suitable for later synthesis.

Research status must distinguish at least: not started, in progress, evidence collected, proposal drafted, independently reviewed, and completed for current scope. “Completed” means the stated research questions have been investigated to the declared scope; it does not mean a vector has been accepted.

## 4. Research coverage gaps

The current repository has substantial work on requirement evolution, dependency analysis, proof boundaries, artifact storage, compilation caching, runtime, backends, and Git. It does not yet constitute a complete exploration of the language design space.

The highest-leverage gaps to address explicitly are:

- A coherent operational and denotational semantic core covering the language constructs beyond the narrow relational-verification fragment.
- A comparative type/effect/ownership/capability-system study.
- A unified model for state, errors, effects, concurrency, and observable behavior.
- A comparison of alternative SPG/IR decompositions and canonical identity boundaries.
- A security and trusted-computing-base model.
- A unified evidence/conformance model spanning tests, proofs, runtime checks, and external components.
- A cross-aspect comparison of interpreter, VM, LLVM, and source-to-source backend strategies.

These are gaps to research, not predetermined design requirements.

## 5. Relationship to the specification space

The taxonomy defines dimensions of research, not a checklist of independent toggles. The eventual option space is constructed from the vectors actually supported by research. The dependency map identifies conditional choices and incompatibilities; the synthesis process then generates valid integrated candidate specifications and compares them as wholes.

See [Research Dependency Map](RESEARCH-DEPENDENCY-MAP.md) for sequencing and cross-aspect relationships.
