**Date** · 2026-11-21  
**Baseline** · `b52ba2fb32e2c315997c74d8924c2c9aaeb177dc`  
**Status** · Scoped Lean implementation and evidence for [Plan §2.3](../PLAN.md#23-lean-logos-smt-and-solver-integration)

## Question

How can a solver-facing JSON message carry the checked relational query without letting another producer choose the assumptions? SCW-26–30 relate paired source executions to a Lean formula, establish the QF_LIA profile, and bind each symbol to exactly one declaration. The existing version-2 JSON decoder validates fields and supports a separate structural CPC comparison. Schema validation alone accepts well-formed observations supplied by the sender. [Scenario 34](RESEARCH-SCENARIO-34-SOURCE-TO-QUERY-SEMANTIC-CORRESPONDENCE.md#76-qf_lia-admissibility-and-external-wirechecker-boundary)

| Boundary | Benefit and cost |
|---|---|
| Decode a supplied version-2 envelope | Supports interchangeable producers. A separate authority must verify that the assumptions match the source. |
| Rebuild a Lean-owned envelope and require exact bytes | Simple to audit and rejects altered assumptions, declarations or ordered observation fields. A relay must preserve the compact encoding byte for byte. This experiment implements this profile. |
| Decode and compare typed terms under a verified bijection | Could accept harmless formatting and support compatibility with separately implemented emitters. It needs a definition and proof of decoded term preservation and explicit handling of malformed or duplicate keys. |

## Implementation and checks

`sourceEnvelope` compiles the typed program with its selected factor and observation contract. It obtains the two ordered assumptions and declarations through the existing lowering. Shared symbols retain their internal `i_N` names. The selected left and right symbols add `_L` and `_R` to those internal names, respectively. The encoder uses that same lookup for declarations and occurrences. The envelope carries the selected factor ID and records the result sort and ordered observed state IDs and sorts.

`decodeSourceEnvelope` first recomputes the expected bytes from the source inputs. It passes the exact match to the existing decoder. Lean checks `decodeSourceEnvelope_matches`: every successful decode consumed the exact bytes produced by `sourceEnvelope` for that program, scope, factor and contract.

| Control | Observation |
|---|---|
| Int factor with a Boolean guard, shared inputs, a negative coefficient, unary negation and observed state | The generated envelope passes the existing decoder and the source check with the expected declaration names. |
| Bool factor with an Int state observation | The generated envelope passes with the expected Bool pair names. |
| Changed observation formula, selected left name, or contract string | All three still decode as version-2 JSON. The source check rejects all three. |
| Extra whitespace, replay under another factor or contract, and selecting a state slot as the factor | All four are rejected by the source path. |

The theorem establishes the byte boundary. A general theorem that the renamed and decoded terms have the same denotation is still open. The existing Python emitter has its own naming and serialization choices. This profile can relay Lean-generated bytes, and interchange with another emitter requires an explicit compatibility study. The experiment does not route CPC acceptance through the source gate or establish that a supplied proof is valid. Those are the next SCW-32–34 boundaries. [Proof trust model](LLMLang-FORMAL-VERIFICATION.md)

lake update --keep-toolchain
