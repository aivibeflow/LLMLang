# Исследование «Git-интеграция семантических программ и Semantic Diff/Merge» для LLMLang

**Контекст:** Исследование является частью проекта LLMLang (репозиторий [aivibeflow/LLMLang](https://github.com/aivibeflow/LLMLang)), посвящено архитектуре хранения семантического представления программ и их интеграции с Git, а также алгоритмам семантического сравнения и слияния. Документ независим от параллельных исследований (Lean/Logos/QF_LIA) и опирается на существующие материалы репозитория и реальные технологии: Git (объектная модель, драйверы слияния и пр.), Unison, semantic-merge, CRDT-подходы, Bazel/Nix и др.

**Цели исследования:**
- Определить архитектуру хранения семантического графа программы и его версионности.
- Разработать модель «Semantic Diff» и трехстороннего «Semantic Merge» для семантического графа LLMLang.
- Исследовать варианты интеграции этой модели с обычным Git (merge driver, mergetool, атрибуты).
- Предложить прототип поведения (сценарии, тесты) и оценить риски, производительность, удобство миграции.

**Состав отчёта:** Проблематика и варианты решений, обсуждение, выводы и рекомендации, с чётким разделением фактов (с цитатами), гипотез и окончательных предложений. Научные источники и существующие практики приведены для иллюстрации.

## 1. Архитектура хранения семантического графа

Для LLMLang семантическая программа должна представляться не просто деревом исходного кода, а **графом семантических узлов**, каждый из которых имеет уникальную идентичность (`OpHash` и `ImpHash`). Необходимо определить, как этот граф **версионируется** и хранится.

### 1.1. Объектная модель Git

- **Git как хранилище.** В Git все данные хранятся в *контент-адресуемом* хранилище: каждый «объект» (blob, tree, commit) идентифицируется криптографическим хешем содержимого【18†L229-L237】. Например, дерево каталога и его файлы образуют объект типа tree, каждая версия этого дерева (и отдельные файлы, как blob) имеют постоянный SHA-1 (в новых Git – SHA-256) «имя», по которому Git всегда может восстановить их точное содержимое【18†L229-L237】. Разветвлённость веток представлена через объекты commit, которые ссылаются на родительские (или несколько родителей) коммиты, а также на корневой `tree`.

- **Возможности Git.**  Git построен для хранения файловых деревьев с неизменяемой историей. При этом *референции* (refs) – ветки и теги – указывают на вершины графа коммитов, а рефлоги регистрируют историю изменения этих ссылок【18†L220-L229】【18†L242-L250】. Git поддерживает эффективное клонирование (через pack-файлы) и инкрементальное получение изменений (fetch) по SHA. Однако семантический граф LLMLang – не обязательно файловая иерархия, а скорее DAG узлов, связанных зависимостями.

### 1.2. Основные варианты хранения семантических узлов

1. **Git-native (объектно-ориентированный).** Можно представить каждую семантическую сущность (функцию, тип, контракт и т.д.) как отдельный файл или blob и организовать его в tree. Например, корневой `tree` соответствует модулю или файлу, а в нём – отдельные объекты функций. Тогда Git мог бы естественным образом хранить каждый изменённый узел как новый blob и автоматически индексировать их хеши. Однако в такой схеме возникают трудности:
   - Как отразить произвольный граф (а не просто дерево файлов)? Git-дерево – иерархия каталогов, что хорошо подходит для файловой структуры исходников, но семантические узлы могут быть взаимосвязаны (например, пересекающиеся зависимости).
   - Слияние. Обычное текстовое слияние работает на уровне строк. Даже если каждую функцию хранить как отдельный файл, слияние «файлов» всё равно будет текстовым. Sematic-merge (например, [gaurvinayak/semantic-merge](https://github.com/gaurvinayak/semantic-merge)) разбирает код через AST и решает многие конфликты на уровне деклараций【3†L325-L334】, но это всё же синтаксическое решение.
   - Семантические хеши (`OpHash`/`ImpHash`): Git уже хранит хеши объектов, но их вычисление стандартное (над битовым контентом). Для наших целей нужны хеши над *семантическим содержимым* (игнорируя случайные детали форматирования). Git не предоставляет встроенных средств для «канонизации» перед хешированием по собственным правилам.

2. **KV-хранилище (content-addressable DB).** Вместо Git можно использовать отдельное хранилище ключ-значение (например, прототип LLMLang или даже Git Object DB в стороннем режиме) для семантических узлов. Ключом выступает семантический хеш узла (`OpHash` или `ImpHash`). Значение – сериализованный узел (структура). Такой подход родич концепции Unison, где весь код хранится в единой базе (SQLite) с содержательными хешами【14†L97-L101】【15†L172-L181】. Достоинства:
   - Гарантируем *каноничность* идентификаторов: нередактируемость объекта – неизменность семантического содержимого.
   - Можно реализовать специальные правила сериализации перед хешированием (например, упорядочить поля, убрать метаданные).
   - Легко хранить произвольные графы (узлы могут ссылаться на другие по их ключам).
   Минусы:
   - Требуется внешний сервис/движок (служба хранения), чтобы несколько разработчиков имели консистентный view. При клонировании Git нужно также перенести базу (или указатель на удалённый), иначе истории не получится восстановить.
   - Git сам по себе ничего не знает о таком хранилище; придётся определить, что хранится в Git-репозитории и что – в KV.

3. **Гибридный подход.** Комбинация: поддерживать семантический граф в KV, а в Git помещать лишь *минимальные* данные для связи. Например:
   - Git хранит набор «индексных файлов» или отметок, связывающих коммиты с корневым `OpHash` графа. При `git clone` из хранилища извлекаются ссылки на внешние объекты; затем клиент может загрузить соответствующие узлы по хешам из KV или из других репозиториев (как Unison синхронизирует между кодобазами).
   - Вариант: хранить весь граф как один Git-blob (или набор), сериализованный канонически. Но тогда частичные изменения не будут эффективны для Git; придётся каждый раз пересобирать большие файлы.
   - Или: симулировать KV внутри Git: разместить файлы, именованные по хешам, по соответствующим tree, как Git-объекты. Но Git на это не оптимизирован – лучше использовать его для метаданных.

**Проблемы воспроизводимости (clone/fetch):** 
- Если используется внешний KV, необходимо сделать его *расширяемым и переносимым*. Пример из Unison: при клонировании репозитория Unison, все объекты синхронизируются, но Unison использует свой протокол (на основе `Causal` хранилища). Для Git-проекта можно хранить полный DAG коммитов в Git, а содержимое семантического графа – либо включать в коммиты, либо позволять скачивать по требованию. 
- Нужна каноническая сериализация узлов (чтобы разные реализации выдали один и тот же хеш), в противном случае хеши будут дробиться по видам.

*Выводы:* подход с внешним KV (content-addressed) представляет высокую гибкость (как показал Unison【15†L172-L181】), но приводит к усложнению «репликации» через Git. Git-native удобен только для текстовых/AST изменений. Гибридный – наиболее перспективен, но детали требуют проработки. На практике можно начать с прототипа на KV+Git-файлах для прототипа слияния.

## 2. Модель «Semantic Diff» и «Semantic Merge»

Цель – обобщить обычное diff/merge (строковое) до работы с семантическим графом: сравнивать **узлы** и их связи по смыслу, а не по расположению текста.

### 2.1. Semantic Diff

- **Определение разницы:** Между двумя версиями графа важно отличать изменения в структуре (новый/удалённый/переименованный узел), изменения в контракте/содержимом узла, и незначащие изменения (например, метаданные или комментарии). Семантическая разница может быть реализована как обход графов и детектирование по `OpHash`/`ImpHash`. Наличие `OpHash` упрощает обнаружение идентичных узлов (их контракт не изменился), даже если расположение файла или имя функции поменялось.
- **Независимые изменения:** Если в одной ветке добавлен новый узел (функция/контракт), а в другой параллельно добавлен другой узел в том же или другом месте, их можно автоматически объединить. Это аналог сценария «два независимых изменения» – semantic-merge решит его без конфликта【3†L325-L334】.
- **Параллельные изменения одного узла:** Если две ветки изменили разные части одного и того же узла, нужно уметь это разрешать (например, один изменил контракт, другой – тело функции). Нужна политика (см. ниже).
- **Удаление vs изменение:** Если одна ветка удалила узел, а другая – изменила, что делать? Возможные варианты: либо считать конфликтом (как оба пытаются изменить один и тот же идентификатор), либо, например, при удалении более «сильном» действии предпочесть удаление (но это рискованно).
- **Переименование/перенос (Move/Rename):** Если узел просто переименован в одной ветке, а в другой параллельно что-то изменилось в старом имени, важно распознать, что это всё та же сущность. Sematic-merge (и Unison) могут использовать внутренний идентификатор/хеш, а не имя. При правильной сериализации имена не являются частью хеша (опираемся на контракт), тогда пересечения разрешаются корректно.

Базовые правила слияния можно позаимствовать из Unison: при двух диффах (LCA→Alice, LCA→Bob) строятся операции Add/Delete/Update, затем объединяются (см. комбинацию `combineDiffs` в Unison【15†L202-L211】). Например, Unison считает:
- **Add/Add (разные узлы):** считаются независимыми добавлениями (нет конфликта).
- **Add/Add (одинаковые по синтаксическому хешу):** то же добавление – дублируется, нет конфликта.
- **Update/Update (одинакового подузла):** если обе стороны изменили один и тот же узел, это конфликт (CombinedDiffOp'Conflict【15†L202-L211】).
- **Delete/Update:** обе удалили или одна удалила, другая изменила – считается конфликтом или удаление (Unison помечает как конфликт в CombinedDiff).
- **Rebase/Forward:** Если в одной ветке был Fast-forward (одна неделала изменений по сравнению с LCA), просто применяем изменения другой – без слияния.
 
С Semantic Merge (например [gaurvinayak/semantic-merge](https://github.com/gaurvinayak/semantic-merge)) похожая логика: он группирует AST-узлы по идентификаторам (функций, классов) и мёржит их по декларациям【3†L245-L254】【3†L305-L314】. Приведён табличный сравнительный пример: два соседа добавили разную функцию в одно место – Git на текстах выдавал конфликт, а semantic-merge автоматически объединил обе функции【3†L325-L334】.

### 2.2. Трёхстороннее слияние (3-way merge)

При слиянии веток анализ производится относительно общего предка (LCA). Необходимо спроектировать алгоритм на уровне графа:

- **Шаг 1. Поиск LCA.** Используя историю DAG (graph of semantically versioned commits), находим общий предок двух версий. Это как в Unison (вычисление LCA по «causal»-структуре【15†L151-L160】). Если один из графов прямо предок другого, делаем fast-forward.
- **Шаг 2. Подготовка графов.** Сериализовать или представить разности: например, список изменённых узлов на каждой ветке. Это делается путём обхода графа и сравнения хешей (либо аккуратного «diff» двух версий, как в Unison).
- **Шаг 3. Объединение изменений.** По правилу CombineDiffs (Unison) или аналогично – если в обеих ветках добавлено разное, объединяем; если оба изменили одну сущность по-разному – конфликт; если одна удалила, другая изменила – конфликт (либо выбрать вариант удаления). 
- **Шаг 4. Разрешение конфликтов.** В случае конфликта результаты должны содержать маркеры или оба варианта. В Unison предлагается вызвать внешний merge-tool, если установлен (перенести содержимое конфликтных узлов в файл и дать UI для разрешения)【15†L214-L223】. Для LLMLang можно аналогично: либо вручную выбирать, либо реализовать специфический слияльщик контрактов (например, если контракты явно несовместимы, флаговать ошибку).

**Отдельные случаи:**
- **Изменения контракта vs реализации:** Если в одной ветке изменился контракт функции (подпись), а в другой – тело функции, это потенциально конфликт. Можно попытаться «переиндексировать» вызовы (требует дополнительной рефакторинговой логики) или считать конфликтом с необходимостью ручного вмешательства.
- **Изменения зависимости:** Если ветка A переименовала узел X, а B добавила новый узел Y, зависящий от X, нужно поддерживать консистентность. Если переименование отражено в hash-идентификаторах, обе ветки могут корректно ссылаться на один и тот же новый узел.
- **Идентичность и коллизии:** Благодаря криптографическим хешам вероятность коллизии пренебрежимо мала. `OpHash` даёт ид семантической операции, а `ImpHash` – конкретной имплементации (включая детали). Если `OpHash` совпал и структура совпала, это та же операция (см. Unison: одинаковые synhash определяют неизменность)【15†L172-L181】【15†L182-L193】.

*Безопасное автоматическое слияние:* Правила, гарантированно безопасные:
- Автоматически мёржим независимые добавления/удаления разных сущностей.
- Не мёржим автоматом ситуации «удаление vs изменение» или «двойное изменение» – оставляем как конфликт.
- Всегда сохраняем историю и оба варианта при сомнении (см. semantic-merge: «ни хуже, чем Git»【3†L335-L342】).

**Отделение семантической идентичности и provenance:** Сам процесс слияния должен опираться на **фиксированные идентификаторы узлов (OpHash)**, игнорируя такие вещи, как автор, временная метка, комментарии. Метаданные (автор, сообщения коммитов) храним отдельно (Git-рефы, или храним их в отдельных полях узла). Таким образом, одинаковая функция с разными авторами останется одной функцией по `OpHash`, а конфликты – по семантике, а не по исторической информации.

## 3. Интеграция с Git

Git является инфраструктурой VCS; LLMLang должна уважать стандартные команды (`clone`, `fetch`, `commit`, `merge`, `rebase` и пр.) и при этом расширяться.

### 3.1. Git merge driver и mergetool

- **Merge driver:** Git позволяет регистрировать *пользовательский merge driver* через настройки `.gitattributes` или `git config merge.*`. Semantic-merge (см. выше) устанавливается как драйвер для определённых расширений (например, `*.java`)【3†L388-L397】. Аналогично можно сделать «llmmerge» – скажем, все файлы LLMLang кода (*.llm) обрабатывать своим слиянием. При `git merge` Git вызовет наш драйвер с тремя файлами (Base, Local, Remote), и тот должен вывести merged или маркеры конфликта.
- **Mergetool:** При возникновении конфликтов можно интегрировать внешний визуальный инструмент. Как Unison, LLMLang может генерировать временные файлы с разными версиями графа и запустить GUI/CLI (например, поддержка `git mergetool`). Хотя так сложнее (нет текста), можно упрощенно показывать diff на уровне узлов.
- **.gitattributes:** Нужно определить, какие файлы обрабатывать через semantic-merge driver. Возможно, для репозитория LLMLang хранить основное содержимое в специальном формате (например, текстовый AST), и прописать merge=semantic для него. Это позволит Git `merge-file` по умолчанию заменять на LLMLang-слияние.

**Поведение без LLMLang:** Если на машине пользователя нет нашего драйвера, `git merge` свёрзнёт в текстовом режиме или отметит конфликт. Можно указать «fallback: обычный merge». В идеале: если `.gitattributes` настроен, рекомендуется всем участникам иметь LLMLang (либо включать fallback слияние узлов). В крайнем случае Git вернёт конфликты, и их можно решить вручную (но потеряется часть пользы семантического объединения).

**Ограничения и совместимость:** Git требует, чтобы merge driver возвращал корректный статус (0 = чисто, 1 = конфликты). Нельзя изменять уже слитый объект (commit) внутри драйвера (за исключением модификации контента файлов). Также Git никак не понимает семантику узлов – все наши «метаданные» надо помещать в сам текст/объект, иначе Git не будет их трекать. Например, если семантический узел сериализуется в YAML/JSON внутри файла, то Git-мержер работает с этим представлением.

### 3.2. Git-специфичные возможности

- **Git notes/refs:** Технически можно использовать `git notes` для привязки доп. метаданных к объектам commit или tree, но эти объекты меняются при каждом коммите. Скорее полезнее хранить историю семантики в самом графе (например, `version: semantic` в каждом объекте) и ссылаться на Git только для топологии.
- **Merge commit:** После успешного слияния, как обычно, создаём новый коммит, унаследованный от двух родителей. В нём нужно обновить «указатель на корневой семантический узел». Либо (если KV) – в сообщении коммита или специальном файле записать новый root-hash.
- **Branching и tags:** Ветки Git соответствуют версиям семантических графов. Тег можно использовать для сохранения «миграции»: snapshot всей семантики на момент релиза.
- **Доступность команды:** LLMLang-расширения должны легко устанавливаться (пример: `smerge setup` у semantic-merge) и быть интегрированы через config. Поскольку мы не пишем реальный инструмент, предполагаем, что end-user может добавить нашу утилиту как `git merge-tool`.

## 4. Практические эксперименты и прототип

Для валидации архитектуры необходимо прототипирование и тестирование сценариев. Предлагаем матрицу экспериментов:

- **Независимые изменения:** Создать две ветки, где в одной добавлена функция `foo`, в другой – `bar`, и проверить, что merge (с semantic driver) успешно объединяет обе (как в [3†L325-L334]).
- **Переименование vs добавление:** В master есть `fn X`. В ветке A переименовываем `X`->`Y`; в ветке B добавляем `Z`, зависящий от `X`. После merge должны либо обновить ссылку B на `Y`, либо зафлаговать конфликт. Проверить корректность.
- **Удаление vs изменение:** В ветке A удаляем `X`, в B изменяем `X`. Должен возникнуть конфликт. Проверить, что обе версии сохраняются.
- **Изменение контракта vs тела:** В A меняем сигнатуру `fn f(int)`, в B меняем логику `f`. Как разрешаем? Скорее всего конфликт (и сравнить с концепцией Refinement Types).
- **Сценарии с историей:** Сделать несколько последовательных merge-циклов, имитируя много разработчиков.
- **Повреждение KV:** Если KV-хранилище (где хранятся узлы) потеряно или испорчено, но есть Git-репозиторий с commit-ами, можно попытаться:
   1. Клонировать Git.
   2. Инициализировать новую KV.
   3. По commit-ам или записям восстановления получить root-хеши и подтянуть данные (через протокол синхронизации, аналогичен `git fetch`, но для семантики).
   Проверить, что репозиторий восстанавливается (как Unison: `pull`/`clone`).
- **Оценка производительности:** Создать граф из большого числа узлов (моделировать код «зависимости типа» с 10k+ функций). Посчитать время merge (поиск LCA, обход) и размер KV. Оценить нагрузку на сеть (если узлы загружаются) и подсчитать, сколько изменений обрабатывается быстро благодаря хешам (инкрементальность).

## 5. Сравнение с существующими технологиями

- **Unison:** уже рассмотрена система слияния на основе контентных хешей【15†L172-L181】【15†L202-L211】. Unison хранит код в отдельной базе, Git не используется; слияние делается внутри Unison. Идеи: контентные хеши и `combineDiffs` полезны.
- **Semantic-merge (gaurvinayak):** практический инструмент для кода, использующий AST через tree-sitter【3†L305-L314】【3†L325-L334】. Успешно решает ~86% конфликтов автотестами (согласно документации) без регрессий. Поддерживает fallback на текстовый diff. Это подтверждает, что структурный подход эффективен и реализуем.
- **Bazel (Skyframe):** использует DAG инкрементальной компиляции【21†L84-L93】【21†L150-L159】. Принцип: хранение имплитаций вычислений (SkyValues) и автоматический инвалидационный механизм. Аналогично, LLMLang может кешировать промежуточные стадии анализа (хеши, проверка контрактов). Мы можем вдохновиться идеей, что валидность (OpHash) сама по себе является ключом к кешу.
- **Nix:** Контент-адресация в Nix гарантирует воспроизводимость сборок: изменение несущественных атрибутов (URL и т.п.) не ломает хеш«store path»【23†L119-L124】. Это аналогично тому, что в LLMLang изменение метаданных (названия, авторы) не должно менять семантический хеш узла.
- **CRDT:** Не прямо применимо, так как мы всё же используем централизованную модель (Git, branches). При коллективной разработке CRDT-объекты могли бы обеспечить мультимастер, но в Git-воркфлоу хватит текущих сценариев ветвления.
- **Sapling/Plastic SCM:** Plastic SCM поддерживает «GitSync», но архитектурно отличается; не даёт прямых подсказок, кроме идеи «метадата плюс файлы на Git-сервере» (как в [4]). Не является ключевым.
- **Git attributes/notes:** Атрибуты Git могут задавать наш кастомный слияние, а `git notes` теоретически могут хранить дополнительную аннотацию к коммиту (например, список изменённых `OpHash`). Пока это экспериментальная идея.

## 6. Риски и ограничения

- **Сложность внедрения.** Парадигма «семантический merge» сложнее, чем привычная. Может потребоваться, чтобы все участники команды понимали дополнительные команды или инсталляции. Без LLMLang установленных – не будет semantic-merge. (Risk: медленный переход).
- **Производительность.** Вычисление хешей каждого узла, обход графа, может быть дороже, чем текстовый merge, особенно на больших проектах. Однако большинство узлов статичны (OpHash кешируется), а Graph diff – даже быстрее строкового для больших добавлений, где текстовый vs семантический merge отличен (как в [3]).
- **Миграция существующих репозиториев.** Если проект изначально был на обычном коде, переход к LLMLang потребует конвертации в семантический формат. Придётся рассматривать backward compatibility: возможно, иметь опцию «read-only транслитерации» в репозитории.
- **Коллизии и дублирование.** Маломально, но возможность коллизий OpHash существует (если используется не устойчивый алгоритм). Хранение индекса узлов (например, KV) должно быть масштабируемым.
- **Согласованность.** Если KV-слой и Git-слой рассинхронятся (например, кто-то не запушил изменения семантики, а только запушил commit), может возникнуть несогласованность. Нужно механизмы atomic commit: например, include rootHash в коммит.
- **Кэш и инвалидация.** Хеширование позволяет агрессивно кешировать, но надо строго инвалидация при изменении узла. Гарантия: при изменении семантического содержимого узла меняется ImpHash, и всё автоматически считается новым.
- **Формат хранения.** Утечка деталей реализации между репозиториями возможна, если хранить узлы, специфичные для одной реализации LLMLang. Желательно разделять «интерфейс» (контракты) и «имплементацию» (код).

## 7. Рекомендации и решения

**Рекомендованный подход (прототип):** создавать семантический граф в отдельной KV-базе (content-addressable store, возможно, поверх Git Object DB), а в Git хранить *read-only snapshot*:
- В Git сохраняем дерево объектов, где каждое дерево/файл именуется по хешу (например, сохраняем корневой OpHash в одном файле `root.hash` или напрямую индексируем как пустой blob с именем хеша).
- Все семантические узлы хранятся в KV (или в Git как объекты типа blob, но тогда размер repo растёт сильно). Лучше KV: быстрое получение по ключу, дедупликация.
- Для `git clone` мы можем либо включить KV-данные как подмодуль (тяжело), либо требовать отдельной инициализации KV с указанием адреса (как Unison: `ucm clone` просит server URL).
- Merge driver: прописываем для файлов `*.llm` (или другого формата) semantic-merge, который опирается на хеши узлов. Функционально он будет:
  1. Загрузить (или сгенерировать) семантические деревья Base, Ours, Theirs из файлов.
  2. Выполнить merge в памяти по описанной выше модели.
  3. Выдать результат в файл (новый AST или текст).
- Авто-мерж: если нет конфликтов, merge driver возвращает 0, и Git делает автоматический commit. В противном случае маркер конфликт-файл (с <<<< markers) или сохраняет оба варианта.

В **ADR (архитектурном решении)** оформить такой подход как «Proposed»:  
- Решено хранить семантический код вне Git (в KV хранилище), а Git использовать только для версионирования проекций и управления ветками.  
- Альтернативы (чистый Git-объект или всё в Git) отклонены из-за вышеописанных проблем.  
- Факты: Git — content-addressable (идентичность по SHA)【18†L229-L237】; semantic merge-решения (Unison) показали эффективность контентной адресации для merge【15†L172-L181】【15†L202-L211】.  
- Гипотезы: единое хранилище снизит риск дублирования и упростит слияние, а Git-репозиторий останется лёгковесным (несколько ссылок и метаданных); но нужно экспериментально подтвердить workflow «git clone + init-kv + pull-data».

**Ожидаемые выгоды:** точное определение идентичности узлов (по `OpHash/ImpHash`), значительное уменьшение ложных конфликтов (как видно из semantic-merge)【3†L325-L334】, встроенный кешинг (по аналогии с Bazel/Nix) и возможность инкрементальной компиляции. 

**Дополнительная работа:** обеспечить механизмы резервного копирования KV (чтобы не терять данные) и интеграцию CI (например, проверка качества merge в PR). Тщательно описать все операции (`clone`, `push`, `merge`) для команды.

## Заключение

Исследование показывает, что **семантическое слияние** возможно и может решить многие проблемы чистого текстового подхода. Однако для надежности требуется продуманная архитектура хранения. **Предлагаем** использовать контент-адресуемое KV-хранилище семантики и держать минимальную прослойку в Git (например, корневые хеши графа). Git при этом будет оперировать основными ветками и ссылаться на sematic-merge-driven файлы. Это позволит сохранить reproducibility и совместимость (через Git), а также силу семантической идентификации. 

*Литература и источники:* работа Unison по merge【15†L172-L181】【15†L202-L211】, реализация semantic-merge【3†L325-L334】, официальная модель данных Git【18†L229-L237】, модели инкрементальности (Bazel【21†L84-L93】【21†L150-L159】) и content-addressable файловые системы (Nix【23†L119-L124】).

# ADR-0001: Архитектура «Git + семантический репозиторий» для LLMLang

**Статус:** Proposed (предложено)

## Контекст и проблема
LLMLang предполагает хранение программ в виде семантического графа с идентификаторами узлов (`OpHash`, `ImpHash`). Необходимо обеспечить версионирование этого графа, поддержку параллельной разработки (ветки) и семантическое слияние изменений. Git выбран как VCS-заказчик, но его нативная модель файлов/деревьев не приспособлена к семантической репрезентации. Следует решить: как хранить семантику программы – в Git-репозитории напрямую или отдельно – и как встраивать «semantic merge».

## Рассмотренные варианты
1. **Чистый Git (файловая модель):** каждую семантическую сущность представлять файлом/директорией в Git. *Протокол:* полный Git-клон содержит весь семантический код.  
   - *Плюсы:* простота использования Git как есть, все данные сразу в репозитории.  
   - *Минусы:* трудно маппировать произвольный граф в дерево; merge остаётся текстовым (даже при AST-парсере нужен постпроцесс); большие изменения могут затрагивать много файлов (низкая инкрементальность).  

2. **Выделенное KV-хранилище (content-addressable):** семантический граф хранить вне Git (например, в базе, основанной на хешах узлов), Git-репозиторий содержит только метаданные (корневые хеши, ссылки на коммиты). *Протокол:* `git clone` + инициализация доступа к KV-данным.  
   - *Плюсы:* семантические узлы хранятся неизменно по своим хешам, независимые ветки легко объединяются; GN-развитие поддерживается (как в Unison)【15†L172-L181】【15†L202-L211】; возможность глубоко кешировать и оптимизировать.  
   - *Минусы:* требует развёртывания и синхронизации KV (т.е. пользователям нужно настраивать доступ к серверу или распределённую БД); усложняется `clone` (нужно дополнительно копировать KV).

3. **Гибрид:** хранить большинство узлов в KV, но некоторые ключевые файлы или индексы – в Git. Например, Git-репозиторий может содержать синхронизированный дамп графа или отдельные критические таблицы (как cache), позволяя клонировать без KV.  
   - *Плюсы:* уменьшает зависимость от внешнего сервиса при клоне.  
   - *Минусы:* дублирование (двойное хранение), конфликт версий Git vs KV, ещё большая сложность поддержки.

## Решение и обоснование
**Предлагаемое архитектурное решение:** использовать *выделенное контент-адресное хранилище* для семантического графа (например, key-value DB с ключами = семантические хеши) и **Git как средство версионирования только репрезентаций и веток**. Git-коммиты будут содержать ссылки (хеши корней или changed nodes), а весь контент узлов – извлекаться из KV. Merge driver для Git будет вызывать семантический merge, опирающийся на эти хеши (как в Unison и semantic-merge)【15†L172-L181】【3†L325-L334】.

**Обоснования выбора:**
- **Факты:** Git сам по себе – content-addressable система (хеши объектов)【18†L229-L237】, но не предоставляет механизмов семантической нормализации контента (абстрактных хешей). Обзор semantic-merge показал, что семантические AST-слияния решают многие конфликты, которые текстовый merge не умеет【3†L325-L334】. Unison демонстрирует успешное использование контент-хешей при объединении кодовых версий【15†L172-L181】【15†L202-L211】. Nix и Bazel используют аналогичные идеи: инкрементальный кеш и контент-адресуемость для надёжности и воспроизводимости【23†L119-L124】【21†L84-L93】.
- **Гипотезы:** ожидание, что KV-подход упростит merge: если `OpHash` одно и то же, узел считается неизменным (даже при смене мест или имени), что снимет десятки ложных конфликтов. Кроме того, KV позволил бы делиться реализациями (ImpHash) без «мешанины» в репозитории.  
- **Ограничения:** такое решение потребует отдельной настройки среды разработки (необходим ли локальный или сетевой KV), и пользователям может понадобиться LLMLang-клиент для sync (как `ucm pull` у Unison). Также сборка истории становится чуть сложнее (надо синхронизировать KV при push/pull), но выгода в стабильности и скорости слияния оправдывает сложность.

**Следующие шаги:** реализовать прототип: Git-репо с настройкой semantic merge driver и экспериментальным бэкендом на KV (например, LevelDB или SQLite). Проверить сценарии из отчёта. Документировать инструкцию по `clone`/`init`/`push`. Пересмотреть решение после экспериментов – при необходимости скорректировать ADR.

**Последствия:** такое решение задаёт архитектурный инвариант – семантический идентификатор узла (`OpHash/ImpHash`) ≡ SHA-содержимого узла в KV. Все дальнейшие компоненты LLMLang (компилятор, кэш, merge, CI) будут ссылаться на этот принцип. Git останется средством навигации по версиям, а семантика будет гарантирваться KV-хранилищем.
